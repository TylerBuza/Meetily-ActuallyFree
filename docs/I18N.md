# Interface languages (i18n)

Meetily's interface can be shown in English (default) or Simplified Chinese. This
note describes the message layer, what it does and does not cover, and how to add
a string or another language. The interface language is a display preference only:
it is independent of the transcription language (Settings → Transcription) and of
the summary output language (Settings → Summaries).

## Where it lives

| Path | Owns |
| --- | --- |
| `frontend/src/i18n/locales.ts` | Locale registry, default locale, `localStorage` persistence, `<html lang>` sync. |
| `frontend/src/i18n/I18nProvider.tsx` | `I18nProvider` and the `useI18n()` hook (`{ locale, setLocale, t }`). |
| `frontend/src/i18n/translate.ts` | Flattened dictionaries, `{placeholder}` interpolation, fallback order, and `tNow()` for non-React callers. |
| `frontend/src/i18n/types.ts` | `Translatable<T>` (widens English literals), `MessagePath<T>` (dotted key union), `flattenMessages`. |
| `frontend/src/i18n/messages/en/<namespace>.ts` | English text, the source of truth (`as const`). |
| `frontend/src/i18n/messages/zh-CN/<namespace>.ts` | Simplified Chinese, typed as `Messages['<namespace>']`. |
| `frontend/src/components/settings/UiLanguagePicker.tsx` | The Settings → General language picker. |
| `frontend/tests/i18n/messages.test.ts` | Key parity, placeholder parity and fallback checks. |

Message keys are dotted: `namespace.key`, for example `settings.uiLanguageTitle`.
The English tree defines `MessageKey`, so `t('settngs...')` is a compile error. A
Simplified Chinese file that is missing a key, or has an extra one, is also a
compile error. The runtime keeps a last-resort fallback (Chinese → English → key)
so a packaged build cannot render an empty label.

## Using it

```tsx
import { useI18n } from '@/i18n'

function Example() {
  const { t } = useI18n()
  return <button>{t('common.save')}</button>
}
```

- Interpolation: `t('app.meetingDetectedTitle', { app })` with the English message
  `'{app} meeting detected'`. Placeholder names must match in every locale.
- Outside React (module-level helpers, IPC listeners, service functions) use
  `tNow('ns.key')`, which reads the locale last applied by the provider.
- When a constant must store text before rendering, store a `MessageKey`
  (`import type { MessageKey } from '@/i18n'`) and translate at render time.
- `useI18n()` works without a provider and returns English, so components can be
  rendered in isolation (as most tests do) without extra setup.

## Adding a string

1. Add the key to the owning `messages/en/<namespace>.ts` file.
2. Add the same key with the same placeholders to `messages/zh-CN/<namespace>.ts`.
3. Use `t(...)` at the call site. Do not hard-code the English text in both the
   catalogue and the component.
4. Run `pnpm dlx bun@1.3.10 test tests/i18n/messages.test.ts` and
   `pnpm exec tsc --noEmit --incremental false`.

Choose the namespace by the screen that owns the string. Shared button words live
in `common`; the application shell (startup, crash recovery, window events) is
`app`. Keep identifiers, storage keys, IPC command names, model names, provider
ids, language codes and user data out of the catalogues — only human-readable UI
text belongs there.

## Adding a language

1. Add `{ id, label, nativeLabel }` to `LOCALES` in `locales.ts` and extend the
   `Locale` union (it is derived automatically).
2. Create `messages/<id>/` with one file per namespace, mirroring the English
   namespaces and keys, and register it in `messages/<id>/index.ts` and in the
   `MESSAGES` map in `translate.ts`.
3. Extend `tests/i18n/messages.test.ts` to cover the new locale's key and
   placeholder parity.
4. The picker in Settings lists `LOCALES`, so it needs no change.

A partially translated language falls back to English per key. Because the
fallback is per key rather than per screen, ship a language only when its
catalogues are complete.

## Behaviour and limits

- **Default is English.** Existing behaviour is unchanged until the user picks a
  language. The choice is stored in `localStorage` under `meetily_ui_locale`,
  applied immediately (no restart), and reflected in `<html lang>`.
- **Two windows stay in step.** The compact recorder is a separate window; a
  `storage` event applies a language change to it as well.
- **First client render is English.** The static export is built once in English,
  so the provider applies the saved locale right after hydration. This avoids a
  hydration mismatch; in the desktop app the startup check is on screen at that
  moment, so the switch is not normally visible.
- **Dates, durations and relative times follow the interface language.**
  `frontend/src/lib/dates.ts` formats days, clock times, weekday names, durations
  ("45m" / "45分钟") and relative times ("2 days ago" / "2 天前") through the active
  locale. English keeps the system locale it used before.
- **Not translated yet:** strings produced by the Rust backend (native
  notifications, audio-route warnings, some save/import errors), automatic meeting
  titles (`Meeting · Thu, Nov 19 · 4:10 PM`) — the generated prefix and wording are
  data recognised by the native `is_default_meeting_title` check — and user data
  such as meeting titles, contact names and transcript text. These are tracked as
  follow-up work rather than hidden behind the language switch.
- **Tests:** because English stays the reference locale and messages must match
  the previous UI text exactly, existing tests that assert visible English text
  keep passing.
